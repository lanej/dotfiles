# Socrates planning handoff

Read `dialogue.txt` beside this file first. It owns readiness, freezing, reconciliation, and reopening. This companion governs planning, approval, and handoff to execution after readiness.

## Draft the concrete plan

Once readiness passes, draft in this turn without asking permission merely to plan. On resuming a `Validated` version, read any existing draft and continue with the matching draft at its approval or revision step. Draft in this turn if none matches. Give each draft its specification version and a plan revision. Start at `p1` for a new spec version and increment for substantive changes to the plan under that version. Approval and authorization metadata leave the revision unchanged.

For data structure or interface changes, carry the relevant before-and-after and representative exchange from the shared dialogue into the plan before listing implementation steps. Tie the steps to that design, including applicable compatibility work and a check that can expose a broken invariant or boundary. Use the existing contracts directly when they already support the requested behavior.

Include a **Work dependencies** section in the plan itself. Give each task an ID and a short action name, the requirement IDs it satisfies, its deliverable, its predecessor task IDs (or `none`), and the smallest check that would catch a defect in that deliverable. Include these two planning judgments for each task, in the same table or keyed by task ID.

- **Complexity** is low, medium, or high. Base it on the task's uncertainty, interacting constraints, and difficulty of checking the result. Give a short reason when it affects the execution choice.
- **Model and reasoning effort** identify a suitable model or the capability needed, plus the recommended effort. Use a model name and effort setting when the host confirms they are available for that task. Otherwise describe the capability and qualitative effort the task calls for. Choose the lightest combination that can reliably do the work, accounting for the cost of a wrong result as well as complexity. Mark a minimum capability only when the task actually needs it.

Explain which tasks can run together and what must finish before integration or verification. Shared mutable state also constrains scheduling. For a sequential plan, show the sequence. For a single task, one row suffices. Apply repository commit and review conventions.

Include an **Execution handoff** that a fresh executor can use without the original chat. Identify the matching specification and plan revision, the working location and required inputs, the allowed effects, and how to run the task checks and final acceptance checks. State the expected evidence and what to do on a defined failure. Refer to the existing task breakdown and validation contract where they already provide that detail. Include a ready-to-use `$shape` instruction for Codex or `/shape` for Claude Code with the actual absolute session path and both identifiers. For example, `$shape Execute and verify spec v1, approved plan p1, in /path/to/repo/.socrates/20260101-120000/`.

Identify applicable gates using [Shape's review rules](../../shape/SKILL.md) and the repository's policy. Complete required planning reviews before offering execution. Keep a versioned record of their dispositions with the specification or plan so a fresh executor can confirm which version or revision they covered and how blocking findings were resolved.

Use the actual host's planning and write capabilities:

- **Claude Code:** call `EnterPlanMode` when available. Write only the harness-named plan file while plan mode restricts writes; `SESSION_DIR/plan.md` is not writable yet. Include the dependency plan and next action. After any required critique, use `ExitPlanMode` for approval. Do not claim that conversational text alone persisted the plan.
- **Codex in Default mode:** when writes are permitted, save the concrete draft to `SESSION_DIR/plan.md` before returning. Mark it as a draft awaiting approval and present it with the work dependencies. Archive the prior plan under a unique timestamped `history/` path before replacing its content. A progress checklist can track the turn's work, while the execution plan belongs in the draft itself.
- **Codex in Plan mode or with restricted writes:** honor the active mode and use its native plan format when provided (for example, Codex's `<proposed_plan>` block). Present the complete plan with its work dependencies in the current turn and identify which session files still need saving. Use the host's approval interaction when available. A skill cannot switch Codex collaboration modes.

For consequential parallel/shared-state plans, irreversible changes, or consequential accepted uncertainty, obtain independent fresh-context plan critique when available. Give the critic the plan and matching spec, with no inherited author reasoning. Require findings inline and have the planner own any written disposition. Critics do not edit files or dispatch further agents. Resolve actionable findings and record the reviewed revision and disposition in the plan. If independence is required but unavailable, state the unmet gate; do not present an inline review as independent approval. Small sequential low-risk plans need no automatic critique dispatch.

Present the exact draft for the user's choice. Offer approval by itself and approval with explicit instruction to execute and verify. A native approval interaction can convey both only when its action explicitly authorizes execution. A requested revision leaves a draft to revise. If the revision changes a frozen requirement, return through the shared reopen procedure before drafting again.

## Approval and persistence

Once approved by the user, persist the exact draft as `SESSION_DIR/plan.md` when writes are permitted. Preserve the reviewed draft in a unique timestamped `history/` file, even when it was originally presented in conversation. Record that path, the specification version, the plan revision, and the actual approval reference in the approved plan. When execution is also authorized, record that instruction against the approved plan, even if the same message supplies both decisions. Save the matching approved plan before updating the frozen spec to `Status: Planned`.

If writes are restricted after approval, retain the exact approved version and the approval in context and identify which session files are still unsaved. When writes become available, persist those same artifacts. Return to approval if the plan changes. When approval itself is pending, keep the spec at `Validated` and the plan as a draft.

When execution is authorized for the approved plan and writes are permitted, read and apply [Shape's execution and verification procedure](../../shape/SKILL.md#execute-and-verify) in the same turn. When the user approves only, leave the session `Planned` with the execution instruction available for later. Resuming alone preserves the supported state. A later instruction to execute and verify the matching approved plan grants execution authority for its recorded scope.
