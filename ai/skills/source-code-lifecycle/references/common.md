# Source-code lifecycle

Read the project's `.source-code.json` before selecting engineering effort. It records `schema_version`, `policy_version`, `stage`, installed `languages`, skill selections and setup-time versions, optional project `kind`, project `authority` and tool `adoption`, and language-detection evidence. When `skill_storage` is `linked`, read `.agents/source-code-versions.json` for live canonical versions; setup-time versions are observations rather than pins. Canonical edits affect every linked repository; project stages and generated runtimes still require setup or upgrade. Copied installations retain pins. Detection selects guidance and automatically selects the Protobuf check profile unless disabled; `languages` separately identifies installed generated Go, TypeScript, Python, and Protobuf check profiles. Read `AGENTS.override.md` for project routing: it loads the authored `AGENTS.md` and the generated `.agents/source-code.md` policy and version summary. Preserve the authored project requirements. Use the installed testing skill for the current-stage verification strategy. Read [the lifecycle contract](lifecycle.md) when comparing or changing maturity, rather than loading the whole ramp for ordinary project work. If the project has no policy, preserve existing requirements; do not infer a lower stage from apparent immaturity.

When the policy selects a `kind`, read [project kind guidance](kinds.md) and load only the matching kind reference. Kind is explicit and independent of stage; do not infer it or use it to prescribe architecture.

Before choosing application libraries, API protocols, or migration scope, read [the tool-choice policy](tool-choices.md). Load only the configured authority and adoption references; read the catalog only when those policies permit it for the affected capability. Tool choices are binding agent guidance, not an automated dependency gate.

When creating, extending, or reviewing a CLI, read [CLI construction](../../cli/SKILL.md). It owns the language-tool routing and required `skill` / `skill --topic` discovery contract, subject to project authority, adoption, and compatibility.

Apply optional `data-pipeline` and `ui-acceptance` guidance only when listed in the installed skill pins. They are selected explicitly; language detection and workstation tool availability do not opt a project into domain architecture or UI gates.

Apply the selected stage consistently across [Builder](../../builder/SKILL.md), [testing](../../testing/SKILL.md), [comments](../../code-comments/SKILL.md), and installed language guidance. Run `python3 scripts/check-source-code.py LANGUAGE` locally and in CI for the selected stage's generated language gate. Explicit project gates remain binding at every stage.

Use `source-code validate` for structural package and pin checks, and `source-code upgrade --dry-run` to preview releases from the installed command’s source checkout while preserving project selections. Change the stage through `source-code setup --authority AUTHORITY --adoption ADOPTION --stage STAGE --dry-run`, review the added or relaxed obligations, then apply it. A stage is the project's chosen assurance level, not proof of readiness or a release version. A policy version identifies the rules; a source revision and file fingerprints identify installed contents. Four-nines reliability requires a separately defined and measured service objective.
