# Capture a dead end

Document the supplied failed approach using actual conversation evidence. Distinguish a demonstrated technical failure from an untested idea, environmental problem, or disproven assumption. State applicability limits so a failure under one condition does not become a universal prohibition. Ask only about gaps that change the lesson.

Write `dead-ends/YYYY-MM-DD-<brief-name>.md` in the project, creating the directory when needed. Use a unique suffix if that filename belongs to another record; never overwrite it accidentally. Explicit updates preserve useful prior evidence and identify corrections.

Include the applicable information:

- Title, date, tags, and a one-line warning.
- The intended goal, attempted approach, and why it appeared plausible.
- Observed failure: concrete errors, outputs, measurements, and relevant conditions, with source references.
- Confirmed cause versus remaining hypotheses; do not infer a cause merely from a familiar symptom.
- Warning signs, applicability limits, and the reusable lesson.
- A working alternative if actually established, linking to its breakthrough record when available.

Do not invent time wasted, future savings, measurements, or a successful alternative. Missing evidence remains a limitation.

Update `dead-ends/INDEX.md` with a dated title, one-line warning, and relative link; retain existing entries and avoid duplicate links on updates. Check that the saved record and index link are readable. Report their paths and material uncertainty.

An invocation authorizes this project documentation, not global memory, commits, publication, messages, or implementation. Under write restrictions, return the draft and identify unsaved files.
