# Collection and bounded history

DORA consumes Diffline's `review-risk-github-pr-events` topic through its independent `dora-github-pr-events-push` subscription and internal-only, IAM-authenticated `dora-github-evidence` Cloud Run service. Keep Diffline's worker subscription independent. The DORA subscription and dead-letter topic retain messages for seven days, retry with 10–600-second backoff and use a 20-attempt dead-letter policy. No new subscription recovers earlier source deliveries.

The consumer decodes published JSON, retains payload/attributes/provenance and acknowledges only confirmed BigQuery streaming persistence. Projection failures retain raw evidence and return 503 for retry/dead-lettering. Unknown persistence is not success. Inspect backlog, dead letters and processing errors separately. Expanded forwarding carries `github_delivery_id`; evidence-only edits/comments carry `assessment_trigger=false` and must not schedule assessments. Ordinary issue comments are ignored.

From DORA, use `uv run --project github_evidence --locked python -m github_evidence.backfill --scope-file <verified-repositories.json> --repository <owner/name> --start-page 1 --pages 1 --budget-seconds 900`, with `DORA_GITHUB_EVENTS_TABLE=easypost-platform.DORA_bronze.github_pr_events_raw`. The scope file must match verified active registrations. Capture is bounded to 20 PRs/page and 1–5 pages/run. Retry interrupted pages; confirmed object writes survive and deduplicate. API snapshots preserve provenance but cannot recover lost edits/deletions. Verify expanded forward collection before historical writes.

Use `uv run --project github_evidence --locked python scripts/report-evidence-backfill.py` for independent bug/PagerDuty coverage buckets. Its per-query billing cap defaults to 1 GB; after inspecting a bytes-limit error, `--maximum-bytes-billed <positive-bytes>` supplies an explicit bounded override. The report records the cap and exits nonzero for unavailable queries. Before each manual stage execution, check ACTIVE workflow executions and the affected job's unfinished executions. Use execution-specific budgets, not persistent job changes. Run bug capture, resolution and history providers sequentially; run PagerDuty details before correlation. Job success is not a drained queue or complete fixing/introducer search. Read `docs/specs/github-evidence-rollout.md` for current operational evidence and exact stage names.
