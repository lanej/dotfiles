# Local worker acceptance

From `pi/daily-driver`, run `node --import tsx acceptance/local-run.ts` after installing package dependencies and the native `zellij` and `worktree` commands. The harness reads pinned Beads and Dolt binaries from `~/.local/share/beads-service/runtime.json`; set both `PI_DRIVER_NATIVE_BD` and `PI_DRIVER_NATIVE_DOLT` to use explicit binaries instead. `PI_DRIVER_NATIVE_PYTHON` selects the Python interpreter when `python3` is unsuitable.

The fixture creates its own Dolt server, Beads HTTP service, Git repository, managed worktrees, Pi agent directory, journal and Zellij session. It makes Paseo unavailable and records any attempted invocation of its executable. It preserves existing services and terminal sessions. A deterministic loopback OpenAI-compatible provider lets the real interactive Pi acknowledge the accepted bead context and subsequent guidance in the same worker pane. The successful case invokes the real `task_submit_result` tool; failure cases use the native `/task-submit` command. This exercises native Pi input, extension dispatch, tool execution and SDK streaming; it does not assess an external model's reasoning or credentials.

Three separate beads exercise successful verification and confirmed closure, verifier exit code 7 without closure, and an edited brief that requires review without closure. Repeating the successful case's identical start must focus the same registered pane and retain its attempt, process and managed checkout without creating another allocation. Each case exits Pi and reads the task and persisted verification with a fresh driver process. Native manager protection is finished and the clean fixture worktrees are explicitly pruned after the owned session exits.

Set `PI_DRIVER_ACCEPTANCE_OUTPUT` to a task-owned directory to retain each run in its own subdirectory containing `report.json`, per-case native pane text, raw terminal ANSI and the actual loopback provider requests. Without that setting all fixture artifacts are disposable; the JSON report is printed to standard output. Provider requests contain the fixture's prompts and accepted task context, so use only disposable task data.
