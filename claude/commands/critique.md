# /critique — Adversarial Specification Review

Purpose: identify semantic ambiguity, unverifiable success criteria, hidden assumptions, weak validation semantics, and likely false positives before planning or execution.

This command reviews a specification generated by `/socrates`.

## Specification Resolution

Read `$HOME/.claude/commands/socrates/dialogue.txt` for the shared session-resolution,
evidence, and readiness contract. With no arguments, use its session resolver only;
do not run its interview or migration steps. An explicit spec path or session
directory selects that specification directly. Read the spec and any existing
`critique.md` and reconciliation records before assigning new finding IDs.

Critique is read-only toward the specification. If it is a legacy session, assess
actual evidence and recorded answers; a historical confidence score does not prove
readiness. Leave adaptation to `/specify` or `/socrates`.

Write the new report beside the spec as `critique.md`. Before replacing a prior
report, preserve it under a new non-overwriting timestamped filename in `history/`.
Record the exact specification version reviewed. Missing companions fail with the
same named-file/link diagnostic as the invoking Socrates commands.

## Critique Philosophy

Critics do not:
- rewrite the specification
- produce implementation plans
- redefine requirements
- silently mutate intent

Critics only:
- identify ambiguity
- identify hidden assumptions
- identify unverifiable success criteria
- identify weak validation semantics
- identify likely false positives and false negatives
- identify missing authority boundaries or escalation conditions

## Critic Topology

Run at least two independent critique passes when `/critique` is invoked. Give each critic the spec and the shared evidence/readiness contract; avoid conversation context that would fill gaps absent from the artifact.

### Critic 1 — Low Context Executor

Assume:
- no organizational context
- no implicit domain knowledge
- literal interpretation of the specification

Focus on:
- undefined terminology
- ambiguous requirements
- unclear ownership
- missing interfaces
- unclear execution boundaries
- places where literal execution could diverge from intent
- internal contradictions (Harmony violations)

### Critic 2 — Verification Critic

Assume:
- the executor will optimize for visible success metrics

Focus on:
- weak acceptance tests
- gameable validation criteria
- missing regression protection
- silent failure paths
- false positives that could appear successful
- observability gaps
- unrealistic feedback-signal assumptions (infra, live-trigger, cross-service, human-gated review treated as if fast/cheap)
- missing or unusable in-progress feedback where the task needs it; an omitted optional heading alone is not a finding
- unresolved consequential decisions or unsupported claims of user acceptance
- accepted uncertainty without its implications and a concrete check
- contradiction between the decision record and requirements/acceptance criteria

### Optional Critics

Use judgment for additional critique passes:
- systems critic
- operations critic
- security/privacy critic
- minimalism critic

## Output Format

Write findings to the current session artifact:

```text
.socrates/<active-session>/critique.md
```

Or, when `$ARGUMENTS` resolved a specific spec file, write to that spec's sibling:

```text
critique.md
```

Structure:

```markdown
# Critique Findings

Reviewed Specification Version: vN
Reviewed Artifact: <resolved spec path>

## Critical
[Issues likely to produce incorrect execution]

## Major
[Important ambiguities or missing validation semantics]

## Minor
[Clarity or ergonomics issues]

## False Positive Risks
[Ways the task could appear complete while being wrong]

## False Negative Risks
[Missing requirements, constraints, or context]

## Validation Weaknesses
[Weak or unverifiable success conditions]

## Recommended Revisions
[Targeted changes to improve semantic alignment]
```

## Finding identity and resolution

Give each distinct finding a stable F1, F2, ... ID, the affected requirement/decision,
its evidence, its consequence, and a concrete suggested resolution. Preserve an ID
for an unchanged finding; allocate new IDs for new findings, never recycle an ID
for different content. Existing accepted/rejected/deferred findings should not be
reported as new blockers without naming the changed evidence or requirement.

Critique findings are advisory. Reconciliation dispositions live in the spec's
`Critique Reconciliation` section (or an existing legacy `reconciliation.md`) and
follow `dialogue.txt`: accepted, rejected, deferred, or pending. The mere existence
of this report must not restart reconciliation.

The authoritative specification remains the Socrates specification until explicitly revised.
