## Execution & Delegation

Delegate anything touching 2+ files or requiring 2+ tool calls to gather context first, all research (`/research` skill, never run inline), and off-topic side tasks (silently, in background). Challenge for context only when the request is genuinely ambiguous — delegate immediately otherwise. Announce foreground delegations briefly ("Delegating: [reason]"); skip the announcement for background/off-topic work.

See the `report-infra-work` skill and message the `infra-dispatcher` session — never mutate those repos' infra directly yourself.
`Workflow` tool: explicit user opt-in only, never proactive. There is no canned decomposition command — for ad hoc parallel fan-out, author a bespoke `Workflow` script matching the task's shape; for independent tasks against an already-written plan, dispatch each one individually via `Agent` per the routing table above.
Every `Agent` call needs: Context, Domain, Sub-problem, Success (implementation work must include "write tests first" plus the task's own acceptance check — see Proportional Verification below; do not brief "all tests pass" per task), Constraints, Output format. A worktree target needs its absolute path stated explicitly in Context; never pass `isolation: "worktree"` for sequential tasks sharing one pre-existing worktree — it creates a separate new worktree each time. (detail: memory "feedback_worktree_briefing_ambiguity"; more worktree/briefing gotchas in `operating-lessons` skill)
An explicit user instruction to work "in a worktree" must be acted on before any implementation dispatch — call `EnterWorktree`/`git worktree add` yourself, or ask a clarifying question if the phrasing is ambiguous; never let a sub-agent brief declare "no worktree needed" in its place, and never substitute a `git status` check for actually resolving the instruction. (detail: memory "feedback_explicit_worktree_instruction_overridden")
**Never dispatch `fork` when the brief depends on it not writing, not committing, or not running something.** A fork inherits the full parent toolset (Bash/Edit/Write/git) unconditionally; prose restrictions are advisory, never a technical gate. This holds regardless of task shape, scope, or how little pending-work material the fork can see, and regardless of how the rule is worded — prose mitigation has been falsified repeatedly, and the `PreToolUse` gate tried as a replacement was removed for blocking legitimate forks. There is no hard gate now. Use a fresh, non-fork agent (`general-purpose`, `Explore`, or a named implementation agent) any time write-suppression matters, even for a small or purely-research task, and independently verify its output every time. Forks remain fine when writing is expected. (detail: memory "feedback_fork_writes_despite_readonly_brief", "feedback_fork_scope_violation_department_turnover_20260828", "feedback_fork_committed_despite_do_not_commit", "feedback_fork_scope_creep_spec_overwrite")
**Return by reference, not by value.** A sub-agent's prose return averages ~2,600 bytes of your context against ~150 for a three-line receipt — 17.2x over 18 runs (`claude/evals/receipt-contract/`). For any dispatch whose output you will not immediately act on line-by-line, tell the agent: write findings to a named file, reply only with `status:` / `wrote:` / `blockers:`. An agent that always produces prose should carry this in its own definition rather than your brief — a definition is always loaded, a brief's instructions are not. `wrote:` is an unverified claim; check the file exists before relying on it. Which agents can and cannot comply (read-only agents, `code-reviewer`): `operating-lessons` skill, `delegation.md`.
**Delegation vs handoff.** Delegating sheds a *sub-task* while you keep driving (`/delegate`); `/handoff` sheds the *remaining task* when context is already spent. Still working after the agent returns → delegation; leaving → handoff. Never prose-recap a session into a handoff brief — that spends exactly the tokens the handoff exists to escape. (`operating-lessons`, `delegation.md`)
A final-review fix-wave brief must bundle the review's "Recommendations" section by default, not just its numbered Critical/Important/Minor findings — a recommendation phrased as "consider adding..." still needs an explicit park/defer note if excluded, not silent omission. (detail: memory "project_review_recommendation_dropped_from_fixwave")
**Hard gates are `PreToolUse` hooks wired in `.claude/settings.json`**, not CLAUDE.md restatements of the Constitution. A hook that fires on the wrong things is worse than the prose norm it replaces, so treat "add a hook" as a hypothesis to verify against real dispatches, not an automatic fix once written.

A critique agent is discretionary: dispatch it for complex or high-stakes plans where independent scoring (request fit, codebase/convention fit, confidence the plan will work) is worth the cost; skip it for small or low-risk plans. No hard gate enforces this. When you do dispatch the critique, it must be scored by a fresh-context agent (not a fork), not self-assessed by the plan's author. ## Code Changes

**Proportional Verification.** Verification rigor is budgeted, not maximized. Only Josh sets the plan's posture: `explore` requires V0 plus a smoke check per task; `default` requires V1; `harden` requires V2. Absent a declaration use `default` (`methodology` skill). Under `default`, run the affected feature's acceptance check through its real entrypoint, asserting an observable outcome; a check that still passes when you delete the behavior is not one. Break-checks are once per new harness, not per task. V2 runs before the final whole-branch review under every posture; between tasks it runs only under `harden` or the escalation trip-wire below, which overrides any posture upward. If fixes change verified code, rerun affected checks and the branch gate before merge.
Attribution comes from **commit-per-task**, not suite breadth: a per-task commit plus its acceptance check localizes any fault the branch-level run later surfaces (`git bisect`). Per-task checks can miss cross-task interactions; the full branch gate and whole-branch review complement them.
**Escalation trip-wire (stops compounding).** Switch to full-suite-per-task for the remainder of the plan, and say so in narration, when either: (a) the branch-level run or final review surfaces a fault the task's acceptance check should have caught; (b) a task touches shared/global state (schema, config loader, build, auth, a widely-imported module) — a pre-check evaluated when briefing the task, not after the fact.
**The narrowing applies to V1 only — never to review or post-merge CI.** Audited against this repo's history: of 14 post-implementation faults, 12 were found by review of the diff, 2 by post-merge CI, 0 by any test suite at any breadth. Per-task checks buy speed; review and CI buy the quality. Dropping either to go faster is a different and unauthorized trade.
**Review cadence, not test breadth, is the lever on compounding.** Run a bounded wave-boundary review (V3a) over the diff since the last checkpoint, in addition to the whole-branch review (V3b) at the end. Brief every review dispatch with the `methodology` skill's Review Fault Classes; an unguided "review this diff" relies on the reviewer looking in the right place by luck. (Tier table, fault classes, and audit detail: `methodology` skill, Verification Rigor Tiers.)
**Record the detector.** A commit fixing a fault found after the code was written carries a `Detected-By: V<n>` trailer (`V0`–`V4`, or `user`). This is the only measurement the tier model has.
This is a speed/quality tradeoff Josh set deliberately: accept a local, short-lived error rate; do not accept a compounding one or one that loses attribution to its cause.

Break new test harnesses post-red to confirm they can actually fail before trusting green. See `methodology` skill for extended reference.
A break-check must never use `git checkout`/`git restore` or `cd` outside the target dir — break manually (stub/comment out, confirm red, undo) instead. State this as its own bullet in the dispatch brief, verbatim — a "don't touch files you didn't create" concurrent-session-drift constraint is a different rule and does not cover a sub-agent reverting its own in-progress file. (detail: memory "project_subagent_git_checkout_breakcheck")
More generally: never `git checkout`/`git restore`/`git reset` a diff you didn't make without a fresh `git log` on that exact file first — if you've already flagged a concurrent session this conversation, that's the leading suspect over a sub-agent, and ask before reverting if still ambiguous. (detail: memory "project_concurrent_multisession_repo_drift")
Never use `git stash` to set aside changes for a baseline check — the stash stack is shared across worktrees/checkouts and a pop can silently clobber unrelated WIP. Use a WIP commit instead. (detail: memory "feedback_git_stash_recurring_despite_inline_prohibition")
Before finalizing a doc/config edit, grep for dependent claims elsewhere in the same and sibling files, and — for any renamed/removed term — grep the full project before touching any file. (`operating-lessons` skill: specific failure patterns)
A clean render/build exit code and a passing test suite are not proof the delivered artifact's content is correct — after any change to a rendered document's markup/escaping/fence convention, read the actual output text (extracted PDF text, rendered GFM/HTML) and grep it for raw source syntax that should have been consumed. (detail: memory "feedback_render_content_not_just_exit_code")
Before applying a newly-defined classification bar/threshold (a size cutoff, a quality gate, a "workable unit" definition) across a batch of new candidates, run its exact metric against the one already-known-correct example on record and confirm it reproduces that number — a provisional, plausible-sounding threshold is not verification, and a too-permissive OR condition can let the bar pass on the wrong half of the definition. (detail: memory "feedback_classification_bar_validate_before_scale")
