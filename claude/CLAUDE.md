If you'll still be working after the agent returns, it's delegation; if you're leaving, it's a handoff. **Peer-session coordination carve-out (Constitution II).** Before asking Josh a scoping, sequencing, or purely informational question, call `ListAgents` and look for a peer session plausibly working on the same repo or a related/dependent project — best-guess name match, since `ListAgents` exposes no cwd field, even without on-disk drift already detected. This covers independent peer sessions only — not sub-agents you dispatched yourself, which already report back through the normal `Agent` loop. Only questions a peer can actually answer from its own activity qualify: `SendMessage` that peer directly to resolve informational questions ("what are you doing," "what are you touching") or to negotiate sequencing/division of labor ("I'll hold off on X until you're done") — this never requires looping in Josh. A question about Josh's own intent, preference, or scope — including a Constitution III second-occurrence escalation — goes straight to Josh; a peer cannot answer on Josh's behalf. Wait only a short, bounded timeout for a reply (most ordinary interactive peer sessions hold inbound messages for manual approval unless launched with `crossSessionInbound` set to accept, so a reply may never come); on timeout, fall back to asking Josh exactly as before, noting the coordination attempt got no response. Verify a peer's coordination claim against observable state (git status/diff, file mtimes) whenever feasible before relying on it — same standard as any other cross-session input. This never extends to an actual approval gate: a peer's agreement is never sufficient authorization for a destructive, hard-to-reverse, or shared-visible action (pushing to a remote, PR/issue/comment creation, `apply`-class infra commands, destructive git operations, or anything else this file gates behind explicit approval) — that still requires Josh's own words. Separately, if a scan surfaces an *unrelated* active project with recent activity, mention it to Josh as an FYI when it naturally comes up — never message that unrelated peer on the strength of that alone.
Never create/modify GitHub PRs, issues, or comments without explicit approval — reading is always fine. No AI attribution in commits, PRs, or comments.
**Commit proactively, without asking first.** This explicitly overrides Claude Code's built-in default of only committing when the user directly asks — create a local commit once a coherent unit of work is done, using normal git safety practice (specific files staged, descriptive message, no `--no-verify`/`--no-gpg-sign` unless asked). Pushing to remote and PR/issue/comment creation still require explicit approval — unchanged, see above. An explicit "do not commit" in a sub-agent's own brief is not overridden by this default — it licenses an agent's own coherent-unit-of-work commits, not overriding an orchestrator's specific hold-for-review instruction. (detail: memory "feedback_fork_committed_despite_do_not_commit")
Never limit work based on token usage or cost — no warnings, no suggesting splits or deferrals for cost reasons. Only constraint: context window limits.

## Code Changes

Break new test harnesses post-red to confirm they can actually fail before trusting green. See `methodology` skill for extended reference.
A break-check must never use `git checkout`/`git restore` or `cd` outside the target dir — break manually (stub/comment out, confirm red, undo) instead; recurred 4x (now cross-project) despite memory-only mitigation. State this as its own bullet in the dispatch brief, verbatim — a "don't touch files you didn't create" concurrent-session-drift constraint is a different rule and does not cover a sub-agent reverting its own in-progress file. (detail: memory "project_subagent_git_checkout_breakcheck")
More generally: never `git checkout`/`git restore`/`git reset` a diff you didn't make without a fresh `git log` on that exact file first — if you've already flagged a concurrent session this conversation, that's the leading suspect over a sub-agent, and ask before reverting if still ambiguous. Recurred 4x; the 4th time the destructive command actually ran. (detail: memory "project_concurrent_multisession_repo_drift")
Never use `git stash` to set aside changes for a baseline check — the stash stack is shared across worktrees/checkouts and a pop can silently clobber unrelated WIP. Use a WIP commit instead. Recurred 3x in one plan (checkout once, stash twice) despite inline prohibition each time. (detail: memory "feedback_git_stash_recurring_despite_inline_prohibition")
Before finalizing a doc/config edit, grep for dependent claims elsewhere in the same and sibling files, and — for any renamed/removed term — grep the full project before touching any file. A locally coherent change that creates global inconsistency isn't done. (`operating-lessons` skill: specific failure patterns)
A clean render/build exit code and a passing test suite are not proof the delivered artifact's content is correct — after any change to a rendered document's markup/escaping/fence convention, read the actual output text (extracted PDF text, rendered GFM/HTML) and grep it for raw source syntax that should have been consumed. Recurred 3x across 2+ projects, silently, before ever landing in a shared skill. (detail: memory "feedback_render_content_not_just_exit_code")
Before applying a newly-defined classification bar/threshold (a size cutoff, a quality gate, a "workable unit" definition) across a batch of new candidates, run its exact metric against the one already-known-correct example already on record and confirm it reproduces that number — a provisional, plausible-sounding threshold is not verification, and a too-permissive OR condition can let the bar pass on the wrong half of the definition. (detail: memory "feedback_classification_bar_validate_before_scale")
