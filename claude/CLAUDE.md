## Execution & Delegation

Delegate anything touching 2+ files or requiring 2+ tool calls to gather context first, all research (`/research` skill, never run inline), and off-topic side tasks (silently, in background). Challenge for context only when the request is genuinely ambiguous — delegate immediately otherwise. Announce foreground delegations briefly ("Delegating: [reason]"); skip the announcement for background/off-topic work.
Hit a bug or want a small feature in one of Josh's `easypost-sandbox` tool/MCP-server repos that isn't your job right now? See the `report-tool-work` skill — don't work around it silently.
Hit a need for an infra change (GCP resource, IAM grant, DNS record, GitHub org/repo setting, Jira config) in `easypost-enterprise-platform-infra` or `enterprise-platform-bootstrap` that isn't your job right now? See the `report-infra-work` skill and message the `infra-dispatcher` session — don't work around it silently, and never mutate those repos' infra directly yourself.
`Workflow` tool: explicit user opt-in only, never proactive. There is no canned decomposition command — for ad hoc parallel fan-out, author a bespoke `Workflow` script matching the task's shape; for independent tasks against an already-written plan, use `subagent-driven-development`.
Every `Agent` call needs: Context, Domain, Sub-problem, Success (implementation work must include "write tests first" plus the task's own scoped check — see Proportional Verification below; do not brief "all tests pass" per task), Constraints, Output format. A worktree target needs its absolute path stated explicitly in Context; never pass `isolation: "worktree"` for sequential tasks sharing one pre-existing worktree — it creates a separate new worktree each time. (detail: memory "feedback_worktree_briefing_ambiguity"; more worktree/briefing gotchas in `operating-lessons` skill)
An explicit user instruction to work "in a worktree" must be acted on before any implementation dispatch — call `EnterWorktree`/`git worktree add` yourself, or ask a clarifying question if the phrasing is ambiguous; never let a sub-agent brief declare "no worktree needed" in its place, and never substitute a `git status` check for actually resolving the instruction. (detail: memory "feedback_explicit_worktree_instruction_overridden")
**Never dispatch `fork` when the brief depends on it not writing, not committing, or not running something.** A fork inherits the full parent toolset (Bash/Edit/Write/git) unconditionally; prose restrictions are advisory, never a technical gate. This holds regardless of task shape, scope, or how little pending-work material the fork can see, and regardless of how the rule is worded — prose mitigation has been falsified repeatedly, and the `PreToolUse` gate tried as a replacement was removed for blocking legitimate forks. There is no hard gate now. Use a fresh, non-fork agent (`general-purpose`, `Explore`, or a named implementation agent) any time write-suppression matters, even for a small or purely-research task, and independently verify its output every time. Forks remain fine when writing is expected. (detail: memory "feedback_fork_writes_despite_readonly_brief", "feedback_fork_scope_violation_department_turnover_20260828", "feedback_fork_committed_despite_do_not_commit", "feedback_fork_scope_creep_spec_overwrite")
**Return by reference, not by value.** A sub-agent's prose return averages ~2,600 bytes of your context against ~150 for a three-line receipt — 17.2x, measured over 18 runs (`claude/evals/receipt-contract/`). For any dispatch whose output you will not immediately act on line-by-line, tell the agent: write findings to a named file, reply only with `status:` / `wrote:` / `blockers:`. Custom agents that always produce prose should carry this in their own definition rather than in your brief (`document-summarizer` does) — a definition is always loaded, a brief's instructions are not. For write-capable built-ins such as `general-purpose`, state the contract in the brief. Read-only agents (`Explore`, `Plan`, and any custom agent without `Write`) must return concise findings inline; do not request a file they cannot create. Use a write-capable agent when a file is required. `wrote:` is an unverified claim — check the file exists before relying on it. `code-reviewer` has no `Write` tool and structurally cannot comply; leave it returning prose or grant it `Write` deliberately.
**Delegation vs handoff.** Delegating sheds a *sub-task* while you keep driving (routing table: `/delegate`). `/handoff` sheds the *remaining task* when the session's context is already spent — it writes a ~15-line pointer brief and lets a fresh sub-agent rebuild context from the session JSONL, so the synthesis cost lands in a disposable context. If you'll still be working after the agent returns, it's delegation; if you're leaving, it's a handoff. Never prose-recap a session into a handoff brief — that spends exactly the tokens the handoff exists to escape.
A final-review fix-wave brief must bundle the review's "Recommendations" section by default, not just its numbered Critical/Important/Minor findings — a recommendation phrased as "consider adding..." still needs an explicit park/defer note if excluded, not silent omission. (detail: memory "project_review_recommendation_dropped_from_fixwave")
**Hard gates are `PreToolUse` hooks wired in `.claude/settings.json`**, not CLAUDE.md restatements of the Constitution. A hook that fires on the wrong things is worse than the prose norm it replaces, so treat "add a hook" as a hypothesis to verify against real dispatches, not an automatic fix once written.
**Plan Mode: always start fresh.** Wipe the plan file for a new task rather than appending — it's a point-in-time snapshot, not a history. An `Agent(model="opus")` critique is discretionary: dispatch it for complex or high-stakes plans where independent scoring (request fit, codebase/convention fit, confidence the plan will work) is worth the cost; skip it for small or low-risk plans. No hard gate enforces this. When you do dispatch the critique, it must be scored by the critique agent, not self-assessed by the plan's author. (detail: memory "feedback_shape_gate_violations"; alignment score definition in memory "feedback_plan_alignment_score")
**Plan Mode: always end with a summary.** Close every plan with a short "Summary" section — a sentence or two of the overall approach, the three alignment scores from the Opus critique if one was run as a table (score / value / why not 100%, per memory "feedback_plan_alignment_score"), then a flat bulleted list of the concrete actions it will take, in order. This is what the user reads to approve or redirect, so it must stand alone without requiring a re-read of the full plan body.

## Code Changes

**Proportional Verification.** Verification rigor is budgeted, not maximized. Per task, run only the narrowest check that would catch a fault in *that task's own deliverable* — the changed file's/package's tests, a type-check on the diff, a targeted grep. Not the full suite. The full suite runs once per branch, as a gate before the final whole-branch review, not between ordinary tasks. The per-task floor follows the plan's declared posture — `explore`/`default`/`harden`, defined in the `methodology` skill; absent a declaration it is `default`, and only Josh sets it, never you. The escalation trip-wire below overrides any posture upward. If fixes change verified code, rerun affected checks and the branch gate before merge.
Attribution comes from **commit-per-task**, not suite breadth: a per-task commit plus a scoped check localizes any fault the branch-level run later surfaces (`git bisect`). Scoped tests can miss cross-task interactions; the full branch gate and whole-branch review complement them.
**Escalation trip-wire (stops compounding).** Switch to full-suite-per-task for the remainder of the plan, and say so in narration, when either: (a) the branch-level run or final review surfaces a fault a scoped check should have caught; (b) a task touches shared/global state (schema, config loader, build, auth, a widely-imported module) — a pre-check evaluated when briefing the task, not after the fact.
**The narrowing applies to V1 only — never to review or post-merge CI.** Audited against this repo's history: of 14 post-implementation faults, 12 were found by review of the diff, 2 by post-merge CI, 0 by any test suite at any breadth. Per-task checks buy speed; review and CI buy the quality. Dropping either to go faster is a different and unauthorized trade.
**Review cadence, not test breadth, is the lever on compounding.** Run a bounded wave-boundary review (V3a) over the diff since the last checkpoint, in addition to the whole-branch review (V3b) at the end. Brief every review dispatch with the `methodology` skill's Review Fault Classes; an unguided "review this diff" relies on the reviewer looking in the right place by luck. (Tier table, fault classes, and audit detail: `methodology` skill, Verification Rigor Tiers.)
**Record the detector.** A commit fixing a fault found after the code was written carries a `Detected-By: V<n>` trailer (`V0`–`V4`, or `user`). This is the only measurement the tier model has. (Not AI attribution; the no-attribution rule is unaffected.)
This is a speed/quality tradeoff Josh set deliberately: accept a local, short-lived error rate; do not accept a compounding one or one that loses attribution to its cause.

Break new test harnesses post-red to confirm they can actually fail before trusting green. See `methodology` skill for extended reference.
A break-check must never use `git checkout`/`git restore` or `cd` outside the target dir — break manually (stub/comment out, confirm red, undo) instead. State this as its own bullet in the dispatch brief, verbatim — a "don't touch files you didn't create" concurrent-session-drift constraint is a different rule and does not cover a sub-agent reverting its own in-progress file. (detail: memory "project_subagent_git_checkout_breakcheck")
More generally: never `git checkout`/`git restore`/`git reset` a diff you didn't make without a fresh `git log` on that exact file first — if you've already flagged a concurrent session this conversation, that's the leading suspect over a sub-agent, and ask before reverting if still ambiguous. (detail: memory "project_concurrent_multisession_repo_drift")
Never use `git stash` to set aside changes for a baseline check — the stash stack is shared across worktrees/checkouts and a pop can silently clobber unrelated WIP. Use a WIP commit instead. (detail: memory "feedback_git_stash_recurring_despite_inline_prohibition")
Before finalizing a doc/config edit, grep for dependent claims elsewhere in the same and sibling files, and — for any renamed/removed term — grep the full project before touching any file. (`operating-lessons` skill: specific failure patterns)
A clean render/build exit code and a passing test suite are not proof the delivered artifact's content is correct — after any change to a rendered document's markup/escaping/fence convention, read the actual output text (extracted PDF text, rendered GFM/HTML) and grep it for raw source syntax that should have been consumed. (detail: memory "feedback_render_content_not_just_exit_code")
Before applying a newly-defined classification bar/threshold (a size cutoff, a quality gate, a "workable unit" definition) across a batch of new candidates, run its exact metric against the one already-known-correct example on record and confirm it reproduces that number — a provisional, plausible-sounding threshold is not verification, and a too-permissive OR condition can let the bar pass on the wrong half of the definition. (detail: memory "feedback_classification_bar_validate_before_scale")

**1Password.** Never shell out to the `op` CLI directly — use the `mcp__1password__*` MCP tools for all 1Password operations (Environments, variables, local `.env` files, item lookups). An operation with no MCP coverage is a gap to flag, not a reason to fall back to `op` silently. CLI gotcha: `op read`/`op item list` without `--account` searches only the active account — a miss can mean "wrong account" not "doesn't exist"; check both `easypost.1password.com` and `my.1password.com` before concluding an item is missing. (detail: memory "reference_1password_dual_account_op_lookup")
**Sandbox retries.** Before every `dangerouslyDisableSandbox: true` retry, narrate the sandbox restriction that caused the failure AND mention `/sandbox` manages restrictions — every bypass, not just the first. Treat the omission as the default failure mode: check explicitly before each bypass. (detail: memory "feedback_sandbox_command_mention_omitted")
